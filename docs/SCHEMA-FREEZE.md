# product.v1 — schema freeze record

**Frozen:** 2026-09-10
**Schema id:** `nextbridge.dev/product/v1`
**Gate:** two radically different products described by one schema, with no
field invented for either alone and no field rendered meaningless by absence.

---

## The freeze test

| Question | RepoCode | Block Builder | Verdict |
|---|---|---|---|
| Did it need a field no other product could use? | No | No | Pass |
| Did any field become meaningless rather than merely absent? | No | No | Pass |
| Is an empty list readable as complete? | `plugins: []` | `plugins: []`, `integrations: []` | Pass |
| Did it need an escape hatch (free-form object, `extra:`)? | No | No | Pass |

Both manifests validate clean across all three layers against their real
repositories. `node scripts/validate.mjs --repos ..` reports zero errors.

## What each product proved

**RepoCode** — four interface types in one product (`cli`, `mcp`, `library`,
`github-action`); three npm packages under a single distribution channel; an MCP
interface carrying a seven-tool list and two resource templates; an
`integrations[]` entry with `external: true` while internal integrations stay
empty; and the absent-plugin case.

**Block Builder** — `runtime.host` for a product that runs inside another
application; `http-endpoints` for handlers registered into a host rather than a
standalone server; a scoped npm package; a single-command CLI; a `user` set with
no overlap with RepoCode's; and a product whose `plugins` and `integrations` are
both empty and which still reads as fully described.

## What the two products did **not** prove

Stated plainly, because it bounds what "frozen" means here.

| Unproven | Why | Where it gets proved |
|---|---|---|
| `plugins[]` against a real product manifest | Neither Phase 1 product ships a plugin | **Proved.** `code-comrades` and `graphpowers` both declare one, and both plugins were installed from the compiled marketplace |
| `runtime.python`, `distribution.channel: pypi`, `desktop-binaries`, `gemini-cli-extension` | No Python or desktop product was described yet | **Proved** by `project-charter`, `graphpowers`, and `package-pilot` |
| `interfaces[].type: desktop-app`, `pre-commit-hook` | Same | **Proved** by `package-pilot` and `project-charter` |
| `maturity: experimental` | Both described products were `stable` | **Proved** by `edge-compat-check` |
| `distribution.channel: smithery` | `project-charter` ships `smithery.yaml` but publishes no registry id anywhere | Still unexercised. The channel requires an `id`, and inventing one would be worse than omitting the channel |
| `integrations[].status: verified`, and therefore R-REF4 against a real manifest | The one candidate, GraphPowers → Graphify, is `supported`: the canary that would verify it is not installed under `.github/workflows/` | Still unexercised |

All nine products are now described, and the schema absorbed the remaining five
without gaining a field, an escape hatch, or an enum value: every type and
channel they needed was already in the vocabulary the Phase 0 audit produced.
Adding a **value** to an existing enum remains a v1-compatible change. Adding or removing a
**field**, or changing a field's meaning, is not, and requires `product.v2`.

## Frozen surface

Required: `schema`, `id`, `name`, `description.short`, `problem`, `user`,
`capabilities.core`, `interfaces`, `distribution`, `runtime.language`,
`license`, `maturity`.

Optional: `description.long`, `capabilities.secondary`, `runtime.node`,
`runtime.python`, `runtime.os`, `runtime.host`, `plugins`, `integrations`.

Deliberately excluded, and staying excluded:

| Not in the schema | Why |
|---|---|
| `version` | Read it from the package manifest. A second copy drifts |
| `keywords` | Already in package metadata |
| `homepage`, `repository` | Ecosystem-owned (`registry.yaml`) and derivable. Duplicating the repository URL is exactly how the `project-charter` / `saadat-dev` defect happened |
| `family`, `pillar`, positioning | Ecosystem-owned |
| Health scores, popularity, certification | Not being built |
| `interfaces[].type: claude-code-plugin` / `gemini-cli-extension` | A plugin is declared once, in `plugins[]`. Excluding the types from the interface vocabulary makes double-declaration structurally impossible rather than a rule to enforce (decision D4) |
| `distribution.channel: claude-code-marketplace` | Generated by the compiler from `plugins[]`. Hand-authoring it would create the second source of truth the model exists to prevent |

## Changes made after the Phase 1 plan was approved

| Change | Reason |
|---|---|
| `interfaces[]` vocabulary excludes plugin types entirely (D4) | The plan proposed keeping them and rejecting duplicates with a rule. Removing them is strictly stronger and needs no rule |
| Taxonomy uses explicit `categories` and `capabilities` maps, and requires `category` on every capability | The audit's §22 draft mixed parents and leaves in one map, leaving "is this a category or a capability?" ambiguous and letting an orphan drift in unnoticed |
| Taxonomy drops the `products` field | It would be a second source of truth. The compiler computes it |
| `registry.products.<id>.manifest_status` added | Lets all nine be indexed while only two are described, without a rule silently passing on the seven |
| `R-SYNC1` added | The synced snapshot in `manifests/` can go stale against the product repository; nothing in the approved plan caught that |
| `R-TAX1`, `R-DIST1` added | Category resolution and the generated-channel guard. Both fell out of implementation |

All six are refinements within the approved intent. None changes the ownership
model, the artifact set, or the anti-fragmentation rules.

## Amendments after the freeze

### A1 — `interfaces` relaxed to `minItems: 0` (2026-09-10, v1-compatible)

Open question **O1** resolved as option (c): a product is valid when it declares
at least one `interfaces[]` entry **or** at least one `plugins[]` entry.

`code-comrades` has no interface in the vocabulary — its only user-facing
surface is a Claude Code plugin, which decision D4 deliberately keeps out of
`interfaces[]`. Requiring `minItems: 1` would have forced either a `plugin`
interface type or a duplicate declaration, and both reintroduce the
double-source-of-truth the model exists to prevent.

| Change | Kind |
|---|---|
| `interfaces.minItems` 1 → 0 | Loosens a constraint. No previously valid manifest becomes invalid, so it is v1-compatible |
| New layer 2 rule **R-REF9** | A product with neither an interface nor a plugin is an error |

The schema no longer states "a product must have a surface"; R-REF9 does. That
is the trade: the constraint moves from the schema to the rule set, because it
spans two fields and JSON Schema can only express it as a disjunction that
reports uselessly. Nothing became optional in practice.

Rejected alternatives: (a) bare `minItems: 0` with no replacement rule — a
product with no surface at all would validate; (b) a `plugin` interface type
pointing at a `plugins[]` entry by name — a cross-reference D4 removed on
purpose.

## Changing the schema after the freeze

- **Adding an enum value** (a new interface type, distribution channel, user type, integration type): v1-compatible. Add it with the manifest that needs it.
- **Adding an optional field**: v1-compatible, but requires a stated reason and a validation rule that gives it meaning. An optional field nothing checks is documentation.
- **Adding a required field, removing a field, or changing a meaning**: requires `product.v2` and a migration for every manifest.
